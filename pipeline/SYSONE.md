# 手元で動く判定層（Jev の考え方を、ローカルで）

関所（`gate.py`）が「意味」で危険を見つけるための仕組み。**判定する文章はこの Mac から出ない。**

---

## 1. Jev とは何か（調べたこと）

TypeSafe AI が 2026-09-15 に早期提供を始めた **System One モデル**。

| 要素 | 中身 |
|---|---|
| **文章を書かない** | 選択肢・段階・はい/いいえの**確率だけ**を返す |
| **並列サンプラー** | 1トークンずつ生成せず、**1回の計算で全部の確率**を出す。70〜500ms |
| **型が崩れない** | 決めた選択肢の外に出られない。構造エラー 0% |
| **RLCD という学習** | 人の好み（RLHF）でも正解（RLVR）でもなく、**確率の正直さ**を最適化。Brier スコアを報酬に使う |
| **確信度 ≠ 確率** | 確率分布の**尖り具合**。k択なら `(k×最大確率 − 1)/(k−1)`。平たい＝自信なし |
| **使い方の型** | 0.9超＝自動 / 0.5〜0.9＝確認を求める / **0.5未満＝人に回す** |

**重みは非公開・自己ホスト不可。** だからクラウドに出せないデータには使えない。

### 再現実装から学んだこと

| 実装 | 中身 | 学び |
|---|---|---|
| [simple-jev](https://github.com/featherless-ai/simple-jev)（Apache-2.0） | 任意のオープンモデルを分類器にする。**次の1トークンのロジットを読む**。共通の前置きはキャッシュを使い回す | **この方式をそのまま採用した** |
| [Luce](https://github.com/scienthoon/luce) | Qwen3-4B + LoRA + 判定ヘッド。損失に **Brier を混ぜる**。温度スケーリングで較正 | **課題に特化させると、汎用の Jev より強い**（正解率 91.1% vs 75.1%、較正誤差 0.022 vs 0.107） |
| [poorjev](https://github.com/rupeshpoojary9/poorjev) | 小さい含意判定モデル + 温度スケーリング（1.00→2.71）+ **コンフォーマル棄却** | **「誤りをどこまで許すか」を先に決めて、そこから閾値を引く** |
| [SemIf（旧 OpenJev）](https://openjev.com/) | ブラウザ内で完結。入力がページから出ない | 小さいモデルでも成立する |

## 2. 作ったもの（`sysone.py`）

- 型は Jev に合わせる: `Noul`（はい/いいえ）/ `Choice` / `Score`
- **1回の計算**で答えの最初のトークンの確率を読む（MLX / Apple Silicon）
- 同じ文章に複数の問いを投げるとき、**文章部分の計算を使い回す**
- 確信度は Jev と同じ式
- 較正（温度）と閾値は `sysone_calibration.json` から読む

```python
import sysone
r = sysone.ask("相手は実家の近くの病院に通っていると話していた", {
    "others": sysone.Noul("本人以外の人に関する私的な情報が含まれますか？"),
})
r["others"].value        # 'はい'
r["others"].probs        # {'はい': 1.0, 'いいえ': 0.0}
r["others"].confidence   # 1.0
r["others"].ms           # 63.0
```

## 3. Jev と変えたところ（ここが肝）

**Jev の型は「自動化率を上げる」ための設計。** 関所の目的はそれではない。

> 関所の役目は、危ないものを**人の目に確実に届けること**。

なので閾値の決め方を変えた。

- Jev 流: 確信度が高いものを自動処理し、低いものを人へ
- **こちら**: **危ないものが1件も漏れない位置**に基準を置き、そのうえで無駄な印を減らす

棄却（人に回す）は失敗ではなく、**正しい動作**として扱う。

## 4. 実測（`sysone_eval.py` / 作り物の例40件・120判定）

モデル: `mlx-community/Qwen2.5-7B-Instruct-4bit`（Apple Silicon）

| | 値 |
|---|---|
| 1判定あたり | **179ms**（3B なら 78ms） |
| 正解率 | **0.925** |
| Brier（較正前 → 後） | 0.072 → **0.065** |
| 較正誤差 ECE（15分割） | 0.077 → 0.111 |

問いごとの基準（**取りこぼし0件**を保って、無駄な印を最小化）:

| 問い | 基準 | 取りこぼし | 無駄な印 |
|---|---|---|---|
| 他人の私的情報 | 0.690 | **0件** | 21% |
| 秘密情報 | 0.725 | **0件** | **0%** |
| 場所が分かる | 0.774 | **0件** | 6% |

**温度は Brier（確率の良さ）が最小になるよう選んでいる。** その結果 ECE は少し悪化した。
どちらを見るかで最適な温度が違う。**関所では基準（閾値）のほうが効くので、温度は補助的に扱う。**

### 途中で学んだこと

- **3B では足りなかった。** 「他人の私的情報」を判別できず、全部に印がついた（無駄な印100%）。7B で 25% に
- **最初の失敗は、モデルではなく問いの書き方だった。** 「健康・家族・仕事・信条」と例示を絞ったせいで、**「相手の自宅の場所」を拾えなかった**。例示に「住まいや居場所」を足したら、無駄な印が 100% → 25% に落ちた
- **全体の正しさを最適化すると、関所としては使えなくなる。** 温度を強くかけると自信が縮み、「全部人に回す」になった。**目的に合った測り方を選ぶ**
- **自分の作った検証用データが、GitHub の秘密検出に止められた。** 作り物のつもりの Slack トークンが本物と判定された。
  仕組みは正しく働いたが、**「本物そっくりの偽物」は、機械には区別できない**。以降 `EXAMPLE-NOT-REAL` の形にした

## 5. 形と意味、二重にする理由

実際にあった例:

```
「APIキーは sk-proj-9f3k2m1x8b7v6c5z4 を使っている」
  形のチェック → 見逃した（正規表現が sk-proj- の形に対応していなかった）
  意味のチェック → 秘密情報（確率1.00）で検出
```

逆に、意味のチェックが落とすものもある。**どちらも完全ではない前提で、両方を通す。**
そのうえで**最後は必ず人が `review.md` を見る。**

## 6. 特化モデルを作る（進行中）

### Luce をどこまで信じるか（2026-09-21 に検証）

リポジトリは**作られて1日**、スター7、作者1人。ただし中身は率直で、
**作者自身が「4つの Jev 比較のうち2つは同じ項目で比べていなかった」と直している。**

| 信じてよい | 信じるべきでない |
|---|---|
| 手法（LoRA + 較正 + 棄却）は標準的で妥当 | **「91.1% vs Jev 75.1%」は1課題の話**。作者自身が「一般化するな」と明記 |
| 正解をルールで機械生成し、5%わざと壊す設計（堂々巡りを避けている） | 作り物データだけの数字（作者は `[in-synth]` と印を付けて区別している） |
| **「較正は移らない」**という指摘（別課題では温度2.5〜3.3の自信過剰に） | |
| **「本物のラベル100〜300件を用意せよ」**という実践指針 | |
| **「知らない課題では、小さな特化モデルより大きい素のモデルが強い」** | |

→ **いまの 7B（無調整）が簡単に負けるとは限らない。** だから比較を残したまま進める。

### 設計（正確な内容）

| 項目 | 内容 |
|---|---|
| 手法 | **LoRA（低ランク適応）**。アダプタ層の挿入（Houlsby 型）ではない |
| 土台 | `Qwen2.5-3B-Instruct`（4bit 量子化。**重みは凍結**） |
| 学習する部分 | 注意機構の射影に足す低ランク行列。上位16層。保存されるのは数十MBの差分のみ |
| 学習の目標 | **「はい」「いいえ」の1トークンだけ**。問いの部分は損失から外す（`--mask-prompt`） → **推論で確率を読む場所と一致させる** |
| 教師 | `Qwen2.5-32B-Instruct-4bit`（手元）。**確率を直接読む**ので多数決が不要（Luce は多数決で近似している） |
| 学習データ | **作り物のみ 600件**。実際のライフログは一切使わない |
| 評価 | **手作りの例40件**（教師が作ったものではない）。教師の真似度を測らないため |

### 教師の質（実測・2026-09-21）

| | 32B（教師） | 7B（現行） |
|---|---|---|
| 正解率 | **0.975** | 0.925 |
| Brier | **0.029** | 0.065 |
| 較正誤差 ECE | **0.035** | 0.077 |
| 無駄な印（他人/秘密/場所） | 11% / 0% / **35%** | 21% / 0% / **6%** |

**教師も完璧ではない。** 「場所」は 32B のほうが弱い（三軒茶屋を場所と見なさない等）。
**その弱点は生徒に受け継がれる**ので、評価で必ず確認する。

### 学習データの作り方を、途中で変えた（重要）

**最初の方式（教師にデータも正解も作らせる）は失敗した。**
60件つくった時点で「場所」の正例が**ゼロ**。原因は2つ:

1. 生成役が条件に従わず、危ない例をほとんど作らなかった
2. **教師役の「場所」判定がそもそも弱い**（実測で無駄な印35%）

→ **教師に正解を決めさせると、教師の弱点がそのままデータの欠陥になる。**
Luce が正解をルールで機械生成していた理由がここで腑に落ちた。同じやり方に変更:

- 危ない要素を**部品**として持ち、**入れたかどうかで正解を決める**（`distill_build.py`）
- 900件・各問いで はい449 / いいえ451 と均等
- **教師モデルは使わない**（弱点を持ち込まない）

### 評価データの汚染に気づいて作り直した（重要）

最初の評価では 正解率 0.975 と出たが、**評価40件のうち13件（33%）が学習データにそのまま入っていた**。
学習用の部品も評価用の例も、同じ人間（＝この作業をしている側）が書いたため。

→ **言い回しを変えた評価データを新たに36件作成**（`eval/gate_holdout.jsonl`、学習データとの重複0件）。以下はその数字。

### 結果（2026-09-21・重複ゼロの評価36件）

| モデル | 正解率 | 1判定 | 無駄な印（他人/秘密/場所） | 大きさ |
|---|---|---|---|---|
| 無調整 3B | 0.806 | 79ms | 0% / 0% / 0% | 1.7GB |
| 無調整 7B | 0.963 | 178ms | 8% / 0% / 3% | 4GB |
| 無調整 32B（教師役の候補だった） | 0.880 | 812ms | 0% / 0% / 0% | 18GB |
| **学習後 3B（当て板 26MB）** | **0.991** | **84ms** | **0% / 0% / 0%** | 1.7GB + 26MB |

**特化させた 3B が、32B より正確で10倍速い。** Luce の主張（特化 > 汎用）は手元でも再現できた。

学習の実際: 学習対象は全体の **0.216%（665万 / 30億）**、400反復で約11分、ピークメモリ 9.3GB。
学習の損失は 7.4 → 0.001（作り物のデータは完全に覚えた。**だから別データでの評価が要る**）。

### この数字の限界（正直に）

- **評価36件は少ない。** 1件の当たり外れで 2.8ポイント動く
- **学習データも評価データも、同じ人間が書いた。** 「何が他人の私的情報か」の感覚が一致しているので、
  **実際のライフログ（第三者の書き方）では落ちる可能性がある**
- → **実データ100〜300件で測り直すまでは、本番の既定は 7B のまま**にする
