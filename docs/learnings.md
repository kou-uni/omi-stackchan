## 2026-09-19　M0（Mac Studio）

### Bluetooth がエラーを出さずに止まる

- `BleakScanner.discover()` が**永遠に返らない**。例外も出ない
- 中で `CentralManager` の状態更新を待ち続けていた → **macOS の Bluetooth 権限がない**
- 権限は **Python ではなく、親のアプリ（Antigravity IDE）** に要る
- **学び:** 黙って止まる → まず権限を疑う。`asyncio.wait_for` で必ずタイムアウトを付ける

### 公式の連携は「ローカルで閉じる」と両立しない

- webhook は4種類とも Omi のサーバー経由。**便利な入口ほど、クラウドを通る**
- 代わりに、**スマホアプリの役を Mac がやる**。ファームは触らない
- **学び:** 改造の範囲は小さいほうから試す（アプリ側 → ファーム）

### Opus は素直に解けた

- ヘッダ3バイトを捨てて `opuslib` に渡すだけ。decode エラー 0
- `opuslib` は libopus を自力で見つけられない（Apple Silicon の Homebrew は `/opt/homebrew/lib`）→ `ctypes.CDLL` で先に読ませる

### 録音が小さい

- 平均 -46 dB。そのままでも Whisper は読めたが、`loudnorm` を挟む

## 2026-09-20　純正ファームを自分でビルドできた（P0）

- **アプリ本体のイメージが、配布版と中身まで一致した。** 同じソース・同じ版から、同じものが作れることを確認できた
- 無言で止まるインストーラは、**CPU 時間を見れば分かる**（1時間48分でCPU 2秒＝仕事をしていない）
- ベンダー製のツールチェーンは**置き場所が固定**されていることがある。中のコンパイラだけ借りて、周辺は自分で揃えるほうが早い
- **学び:** 「入れる」が失敗したときは、**入れる道具ごと疑う**。配布物を直接取りに行けば、途中の道具を全部飛ばせる

## 2026-09-21　実機への書き込みが1周まわった（※1回目は空振りだった）

- **1回目は「中身が同じもの」を焼いた。** 端末は無事だったが、**実は切り替わっていなかった**
- 原因は**版数**。ブートローダーは「版数が上のものだけ」受け付ける。同じ版数だと**黙って無視する**
- **中身が同じものを焼いたせいで、失敗に気づけなかった。** 安全のつもりの選択が、検証としては役に立っていなかった
- **学び:** 「成功」の判定は、**変化が観測できる形**で立てる。無変化のものをテストに使うと、成功と空振りが区別できない
- 版数を上げ、「次の起動で使う」印をつけて再起動 → **切り替わった**（2026-09-21 08:23）
- 焼く道具は `smpmgr`（Python）。Bluetooth 経由で、アプリ部分だけを書き込む
- **端末側のハッシュが、手元のビルドと一致していた。** 「同じソースから同じものが作れている」と実機からも確認できた
- **学び:** 最初の1回は「何も変わらないもの」を焼くと、手順だけを安全に検証できる

## 2026-09-21　本体を開けずに有線でつなげそう

- 公開されている回路図（Seeed Studio 製）を読んだところ、**磁石で付く充電コネクタに、デバッグ用の端子（SWD）とシリアル（ログ）が出ていた**
- ピン: 1=電源 / 2=リセット / **4=SWDCLK** / **6=SWDIO** / 3,5=シリアル / 外周=GND
- つまり**充電する場所が、そのまま書き込み・復旧の入口**。分解もはんだ付けも不要
- **学び:** 「開けないと無理」と思ったら、回路図を読む。**公開されている資料は、想定より多くを教えてくれる**

## 2026-09-21　「自動で戻る」は今の構成では作れない

- 新しいファームの一時置き場が**本体の外側のフラッシュ**にあるため、試し起動して駄目なら戻す方式が使えない（上書き方式になっている理由）
- 方式を変えるにはブートローダーの入れ替えが必要で、**それは無線ではできない**（有線が必須）
- 代わりに **「書き込みの受け口を絶対に殺さない」** を設計の約束にする。これが実質のやり直し手段になる

## 2026-09-21　勝手に録り続けている

- 純正は電源が入っている限り録音する。止める手段が使う側にない
- しかも「満杯」を示す数字が当てにならず、**止まったように見えて録り続けていた**
- **自前ファームでやること:** 起動直後は録らない。**明示的に始める**（ボタン／Mac からの指示）。録音中は目で分かるようにする

## 2026-09-21　版数を上げると、純正には戻れなくなる

- 上げた版数より低いものは受け付けない = **純正の配布ファーム（0.0.0）は戻せない**
- 対策: **純正のソースから、版数だけ上げた「戻し用」**をビルドして保管（`~/omi-firmware-backup/restore-0.9.0/`）
- **学び:** 前に進む仕掛け（版数の前進）は、**戻り道を塞ぐ**ことがある。塞ぐ前に迂回路を作っておく

## 2026-09-22　「送れた」を「鳴った」と report した

夜の対話（`night.py`）で台本を実機に送り、戻り値 `ok: true` を見て
**「スタックチャンが喋りました」と報告した。実際は実機の電源が入っておらず、音は鳴っていない。**

本人に指摘されるまで気づかなかった。

### なぜ起きたか

`/api/speak` は**実機が居なくても `ok: true` を返す**（Mac 側のプログラムが台本を受理しただけ）。
戻り値のどこにも「鳴ったか」の情報がなかったのに、**成功を示す語だけを見て成功と判断した。**

### 同じ形の失敗を、この日3回している

1. 版数が同じファームを焼いて「書き込み成功」と報告（実際は切り替わっていなかった）
2. 学習の損失が下がったので「学習成功」と判断（実際は判定能力が付いていなかった）
3. **今回**

**共通しているのは「成功の指標を、目的とずれたところに置いた」こと。**
1 は「送信できた」、2 は「損失が下がった」、3 は「API が ok を返した」。
**どれも本当に確かめたいこと（切り替わった / 判定できる / 音が鳴った）ではない。**

### 直したこと

- スタックチャン側（`app/dj/stage.py`）に、**実機の在・不在を返す口**を足した
- `night.py` は**送る前に在・不在を見て**、居なければ送らずに知らせる
- 確認できないときは「**鳴ったかは保証できない**」と明示する

### 学び

**確認したいことを、そのまま測れる形にする。**
「できた」と言う前に、**それは何を観測して言っているのか**を一度立ち止まって確かめる。
